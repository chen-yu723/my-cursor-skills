# 追溯对齐审计

仿 SpecLint（孤儿用例 / 互链缺失 / 含糊措辞）与 traceability-auditor（需求→设计→任务→代码→测试，标记无人接住的需求、无人测试的代码）的方法：**设计决策表 D{n} + 测试用例标题 + 已生成代码**，三方对齐。

## 角色

资深后端开发 + 测试设计。有前端设计文档，或代码已出且含非低代码前端时，增加前端开发视角。只对**可观察规则**做对齐，不评价实现是否优雅。所谓可观察规则 = 「谁、在什么状态、做什么、期望看到什么」。

## 核心判断（先记住这三类，其余都是展开）

| 类型 | 含义 | 裁决标准 | 结论动作 |
|---|---|---|---|
| **不一致** | 同一规则在两份材料里说法不同（含一边有、一边冲突） | 来源核对已通过的设计决策；来源未证实或与需求正文相反时改为待人工 | 候选缺陷：改代码或改用例。来源未证实或与需求正文相反时不自动改任一边 |
| **未覆盖** | 设计/代码里有的规则，用例没承载；或代码分支无测试 | 全覆盖期望 | 漏测：补用例，**不直接判 BUG** |
| **来历不明** | 代码/用例里出现，但设计与用例都没提到的分支/字段/字面量 | 是否该存在 | 标记待人工裁决：补设计 或 删代码/删用例 |

需求正文与设计决策互相矛盾时，类型仍记 **不一致**，裁决列写 **待人工**，不在本步把设计或用例当成唯一正确方。

## 静态能发现 / 不能发现（生产故障反推，不启动系统）

对照多系统生产故障（状态被旁路打脏、按手机号更新到另一条、0 被当成空、热修没进下一版、模板两个角色共用一个变量）。只核材料里写得出来的规则，不推测对方系统当天是否超时。

| 阶段 | 不运行就能判 | 必须连环境或对方系统才知道 |
|---|---|---|
| **A** 设计 + 用例，无代码 | 规则没写死：0 与空、负数、首尾空格、边界日是否包含当天、多方签署时主状态按「一人」还是「全员」聚合、旁路失败（邮件/下载/证据链）是否允许主流程成功、超时后是失败还是未知、已成功能否再发、导入/存量是否走新分支、合同有效期从哪次上传起算、期限单位（年/月） | 某一行把字段赋错、热修没合并、生产流程图和开发不一致、对方返回值、网络与白名单 |
| **B** 代码已出，仍不部署 | 设计字段 vs 赋值；模板占位符是否两角色共用一个变量；更新/查询条件是否只有手机号、姓名或 `limit 1` 且排序为最早；`\|\|`、三元表达式把 0 变成空；验证码或分页条数写死；日期条件写成「大于今天」；正则写死号段；隐藏字段仍 required；金额 `BigDecimal` 转整型或展示层换单位；文件名只有时间戳、上传路径是常量、锁无过期；热修提交不在待发布分支；DDL 缺字段/缺索引；流程图节点角色、监听器与设计节点表不一致 | 白名单缺 IP、注册中心宕机、CDN 故障、对方主数据本身错误、FTP 偶发断开、客户把无关 sheet 一并导入 |

外部真实报文、偶发时序、脏数据本身不归本 skill。代码里已经写死的顺序（取最早一条）、幂等缺口（无状态判断就重发）、空值分支，归阶段 B。

## 输入材料

按阶段给，缺哪份就在哪阶段说明「该阶段无此输入」：

1. **设计决策表**（可选。如 `*-设计决策.md` 里的「决策结论」，每行一个 D1…Dn）——已经拍板的结论，有它时作为裁决基准。没有这份文件不要停，也不要编造 D 编号
2. **开发设计文档**（后端，如 `*-开发设计.md`，§4 实现设计 + §2 流程 + §3 数据模型）。没有设计决策表时，从这里抽可观察规则，报告首行写「无设计决策表，裁决基准改为开发设计」
3. **前端设计文档**（如 `*-前端设计.md`）。阶段 A、B 开始前，在同版本、同需求目录查找。找到就必读，与后端开发设计一起抽可观察规则（入口、按钮显隐、文案、字段校验、跳转、内管还是客户端）。找不到则报告写「本轮无前端设计文档」。后端开发设计里顺带写的页面说明不能代替这份文档。有配套的前端设计决策表时，与后端决策表同样做来源核对，通过的行进入裁决基准
4. **测试用例**（如 `*_测试用例.md`，含 `- 编号：TC-*` 与 `- 预期：`、`- 覆盖：E-*`）
5. **已生成代码**（阶段 B 才需要）：后端 Controller / Service / Listener / DTO / 枚举 / 依赖配置，以及（非低代码前端时）前端页面 / 组件 / 路由 / 接口调用层
6. **来源文档**（有设计决策表时必读，含前端决策表）：决策表「来源」列和文首「输入文档」点到的需求、澄清、接口。路径能从决策表里找到就直接读，找不到再问用户要路径。没有设计决策表则不读

## 来源核对（有设计决策表时，先于用例和代码对齐）

设计决策表仍是实现合同，但只有来源对得上的行才当裁决基准。逐行看「来源」：

| 核对结果 | 这条 D 怎么用 |
|---|---|
| 来源文档里能找到原句，原句推得出该结论 | 进入裁决基准，再拿去对开发设计、前端设计、用例、代码 |
| 来源写明用户或产品已拍板，决策表状态为已批准，且拍板句与结论一致 | 进入裁决基准。需求正文另有不同说法时，这条改标待人工 |
| 来源为空、引用的章节不存在，或原句推不出该结论 | 不进入裁决基准。报告记「来源未证实」，不拿它改用例，也不拿它判代码缺陷 |

来源未证实的行先列出，再做阶段 A/B。开发设计若只实现了这些行，不把「开发设计没写」记成未覆盖。

## 前端参与范围（B 阶段先判定）

B 阶段开始前，先探测前端形态，决定前端是否参与核对：

| 前端形态 | 判定特征 | 参与方式 |
|---|---|---|
| **低代码** | 页面是 JSON 配置（如 `page/*.json` + `menu.json`），无手写 `src/views` | 只抽「接口路径 / 枚举 key / 展示文案 / 字段校验表达式（mustExp/requireExp）」作锚点，**不展开**组件/样式/交互实现 |
| **非低代码** | 手写 `src/views`、`*.vue` / `*.tsx` / `*.jsx`、`package.json` 依赖 | 前端代码**参与三方对齐**，抽前端锚点（路由、组件、文案、接口调用、状态分支） |

- **低代码前端**：按项目约定只核对后端与接口契约侧，前端不产出组件级分歧。
- **非低代码前端**：前端对后端契约的消费（请求路径 / 入参出参 / 枚举值 / 错误文案 / 状态分支 / 路由守卫），与后端、用例同样参与比对；发现前后端不一致按「不一致」处理，裁决以设计为准。

## 统一标签方案（对齐锚点）

三方材料都要能被抽成五类锚点，才能互相比对：

1. **状态/枚举**：业务状态、枚举值 / dictKey 的字面值（如 `PayStatus`、`rtfState`、`PayChannel`）；前端展示/判断用的状态值与后端枚举保持一致
2. **错误码/提示文案**：如「额度不足请检查」等**逐字一致**的字面量；前端拦截/展示的文案与后端返回文案对齐
3. **角色/端**：内管 / 客户端 / 运营 / 用户端等；前端路由守卫、按钮显隐对应的角色与后端鉴权对齐
4. **接口/流程 key**：HTTP 路由 path、RPC 方法名、流程定义 key（processDefKey）、工作流节点 id、前端路由 path、组件 key
5. **字段约束**：必填、长度、类型/精度、格式（正则）、取值域（枚举/码值）。从设计/数据模型抽「每个字段声明的约束」，反查后端校验（`@NotNull`/`@NotBlank`/`@Size`/`@Pattern`、`if(x==null) throw`）、DB DDL（`NOT NULL`/`varchar(n)`/`decimal(p,s)`）、前端 `rules`/`required`/`maxlength`、低代码 `mustExp`/`requireExp` 是否逐项落地。只核「是否声明了校验」；「用户实际能否录进超长/文字」是运行时行为，不归本 skill

比对时按这五类锚点逐条抽，**不是**逐行比对文档。

## 阶段 A：设计↔用例双向对比（代码未出）

**触发**：开发设计文档已输出、代码尚未生成。同版本若已有前端设计文档，一并进入本阶段。
**输入**：开发设计 + 测试用例。有前端设计文档就读。有设计决策表（含前端决策表）就一并读并做来源核对。**无代码**。

### A 步 1 — 抽锚点

- 有设计决策表：只抽来源核对已通过的 D{n}（状态字面值、错误文案、角色、接口/流程 key）。后端表和前端表分开抽，编号不要混用。来源未证实的行不抽。同文件里的「落地约束」、类名、表结构只作对照，不单独变成一条用例缺口
- 没有设计决策表：从开发设计抽状态及下一跳、错误码及当次行为、写明「不包含 / 禁止」的范围，编号用设计章节号
- 有前端设计文档：抽页面可观察规则（哪一端、入口、按钮显隐、文案、字段校验、跳转）。组件选型和样式不单独变成一条用例缺口。编号用前端设计章节号；已有前端决策表且来源通过对的，用该表的 D 编号
- 从测试用例抽：每条 `TC-*` 的「预期」里的可观察规则（`- 预期：`、`- 覆盖：E-*`）
- 后端开发设计与前端设计对同一条可观察规则说法不同 → **不一致**，裁决写待人工，不自动以某一端为准

### A 步 2 — 用例→设计（反查设计漏洞）

逐条用例问：这条「预期」能不能在设计决策表、开发设计或前端设计里找到对应规则？

- 找不到 → **来历不明（用例侧）**：用例臆造了设计没有的规则，或设计漏接了需求
- 找到但值冲突 → **不一致**

### A 步 3 — 设计→用例（反查漏测）

逐条已进入基准的设计决策，以及前端设计里抽出的可观察规则，问：这条规则有没有至少一条用例承载？

- 无任何用例 → **未覆盖**：这条设计规则没有测试兜底，反向推动补用例
- 有，但只覆盖了主路径、没覆盖异常/边界 → **部分未覆盖**（标注）

阶段 A 额外用下面八问扫设计与用例（答不出或两边不一致就进模板 2，不编造运行结果）：

1. 主状态由明细聚合还是由「任一条成功」直接改主表（多方签署、多期还款）。
2. 旁路失败（通知、下载、证据链、抄送邮箱为空）时主流程是否仍成功；再次提交时期望是幂等成功还是报「没有待处理」。
3. 外部调用超时是失败、处理中，还是未知；未知时能否再次发送。
4. 0、空、负数、首尾空格、当天、新号段、中文标点是否各有一条可观察规则。
5. 一对多时用哪一个键（企业 id + 角色，还是手机号/姓名/最早一条）。
6. 存量、导入、未走新流程的老单据走哪条分支。
7. 金额精度、最后一期尾差、期限单位是否写明。
8. 列表分页、跨页勾选、隐藏字段是否仍必填、展示单位是否与入库单位相同。有前端设计文档时，以该文档里的页面规则为准，用例要有对应预期。

### A 步 4 — 含糊措辞

沿用 SpecLint 的含糊措辞信号，只对**可观察规则**：设计/用例里出现「通常/一般/建议/可能/视情况/待确认/⚠️待确认」时，标记为**需人工确认**，不判 BUG（这是规格自身的缺口，不是实现缺陷）。

产出：模板 1（阶段 A 列）+ 模板 2 + 模板 4（仅「不一致/未覆盖/来历不明」三类中该阶段可判的）。

## 阶段 B：代码↔设计↔用例三方对齐（代码已出）

**触发**：代码已生成、测试未启动。
**输入**：设计决策表 + 开发设计 + 前端设计文档（有则带上）+ 测试用例 + **代码**（含非低代码前端）。
**只读**：不启动服务，不跑测试，不改代码，不改用例。只读源码、设计和用例，用搜索把已有用例对到代码位置。

### B 步 0 — 判定前端形态

按「前端参与范围」判定前端是低代码还是非低代码；非低代码前端纳入后续三方对齐，低代码前端只抽接口/文案锚点。

### B 步 1 — 代码↔设计（字面量核对）

把代码里的五类锚点抽出来，与设计决策逐条比：

- 枚举值/dictKey 是否与设计一致（前端判断用状态值、后端枚举值是否同源）
- 错误文案是否逐字一致（设计里的异常句，后端是否原样抛出、前端是否原样展示/拦截）
- 流程 key / 节点 id / 路由 path 是否与设计一致
- 字段名是否一致（DTO 字段、前端表单字段、契约字段）
- 字段约束是否落地（设计声明的必填/长度/类型/格式/取值域，后端校验、DB DDL、前端 rules 是否逐项兑现；缺失 → 不一致）

不一致 → **不一致（候选缺陷）**。设计与代码冲突时，建议动作写「改代码或改用例」，裁决列先写「以已批准设计为准」；若需求正文与该设计互相矛盾，裁决列改写「待人工」。

阶段 B 在字面量之外，按代码形态记一笔（命中即进模板 3，不要求把服务跑起来）：

| 代码形态 | 锚点 | 判定 |
|---|---|---|
| 更新条件只有手机号、姓名、统一社会信用代码，而该键在库里可以对应多行 | 字段约束 | 不一致或来历不明（设计若写了企业 id + 角色仍只用手机号 → 不一致） |
| 查询 `order by` 创建时间升序取第一条，设计写「最新」 | 状态/字段 | 不一致 |
| 费率为 0 时用 `\|\|`、`or` 或三元表达式落成 null | 字段约束 | 不一致 |
| 主表状态在任一明细成功时写成终态，设计写全员完成才终态 | 状态 | 不一致 |
| 签署/付款已成功，后续证据链、邮件、下载抛错后把主状态改回失败或允许无条件重发 | 状态 | 不一致（设计未写该分支 → 来历不明） |
| 合同/报文模板里两个角色共用同一个占位符 | 字段名 | 不一致 |
| 上传路径或文件名是常量或纯时间戳 | 接口/流程 key | 来历不明（设计没写共享路径） |
| 热修提交不在待发布分支；DDL 相对设计少字段或少索引 | 字段约束 | 不一致 |

### B 步 2 — 代码↔用例（按行为核对）

缺口是一条行为，不是一个文件。先把已进入基准的设计规则和代码分支写成一句可观察行为：谁、在什么状态、做什么、期望看到什么。再用接口路径、枚举、错误文案、方法名在用例里搜索。

- 对上了：记下用例位置。一条用例对上某个文件，不算这个文件里的每个分支都已覆盖
- 用例预期和代码的 return、展示文案不一致 → **不一致**
- 用例里找不到这句行为 → **未覆盖**。代码注释或用例注释写「已覆盖」「别处测过」只当作声明，预期里找不到对应行为仍记未覆盖
- 没有同名测试类、测试文件，不单独记成未覆盖
- 代码有、设计和用例都没写 → 交给 B 步 3，不在这里记成未覆盖

每条未覆盖写四项：行为、代码位置、现有用例证明了什么、没证明什么。建议动作只写「补用例」。本步不写用例、不改代码。

### B 步 3 — 来历不明（代码侧）

代码里有，但设计决策 + 开发设计 + 用例**都没提到**的分支、字段、常量、魔法字符串、前端组件/路由 → **来历不明**。逐一列出处，待人工裁决：补设计 or 删代码。

### B 步 4 — 复检设计↔用例

若阶段 A 没跑过，把 A 步 2–4 补一遍，再并入本轮结果。

产出：模板 1（全列）+ 模板 3 + 模板 4（完整三类）。

## 模板 1：追溯矩阵（两阶段共用，B 阶段填全 5 列）

```markdown
| D{n} | 设计规则（可观察） | 用例 TC-* | 代码位置（类#方法 / 字面量 / 前端组件#路由） | 状态 |
|---|---|---|---|---|
| D1 | 流程 key `xxxApply`，不改 `xxx` | TC-XX-XXX | (阶段B填) | ✅/⚠️不一致/❌未覆盖/❓来历不明 |
```

状态列只填四个值：✅ 一致、⚠️ 不一致、❌ 未覆盖、❓ 来历不明。

## 模板 4：分歧报告（最终交付物）

```markdown
# 追溯审计分歧报告

| # | 类型 | 锚点 | 设计说 | 用例说 | 代码写 | 建议动作 | 裁决 |
|---|---|---|---|---|---|---|---|
| 1 | 不一致 | 错误码 | 额度不足请检查 | 额度不足 | 额度不足请检查 | 改用例 | 以设计为准 |
| 2 | 未覆盖 | 状态 | PayStatus=放款失败可重清分 | 无用例 | 已实现 | 补用例 | 不判BUG |
| 3 | 来历不明 | 字段 | 无 | 无 | xyzFlag | 补设计或删代码 | 待人工 |
| 4 | 不一致 | 字段约束 | 名称必填、长度≤2 | 无用例覆盖非法输入被拦截 | 无 `@NotBlank`/`@Size`、前端无 `required`/`maxlength` | 补后端校验+前端 rules | 以设计为准 |
| 5 | 不一致 | 字段约束 | 金额仅数字、2位小数 | TC-xx 预期录入文字报错 | 字段声明 `String` 且无 `@Pattern` | 改类型为 `BigDecimal` 或加格式校验 | 以设计为准 |
```

裁决三原则：
1. **不一致 → 来源核对已通过的设计决策与代码或用例冲突时，以该决策为准**改代码或改用例。来源未证实，或需求正文与已拍板结论不同，裁决列写待人工，不自动改用例、也不自动改设计
2. **未覆盖 → 补用例**，绝不直接把「无用例」写成 BUG
3. **来历不明 → 停下问人**，不自动删代码、也不自动补设计

## 红线

- ❌ 只对比「实现是否优雅/命名好不好」——本 skill 只对可观察规则
- ❌ 把「未覆盖」写成 BUG、把「含糊措辞」写成缺陷
- ❌ 用对方系统当天的返回值、网络故障、客户误操作去判代码。代码里已写明的取数顺序、0 变空、主状态聚合，属于本 skill
- ❌ 低代码前端（JSON 配置页）去展开组件/样式/交互实现——低代码前端只核对后端契约与接口侧
- ❌ 用本 skill 通用口径替代码所在项目自身的分层/依赖规范——项目特定硬伤（如契约模块互引、领域层直连外部系统、DO 进契约模块）按项目 rules/CLAUDE.md 落地核对，仅作「设计落地核对」标记，不套用其它项目的具体规范
- ❌ 阶段 B 启动服务、跑测试、改代码或改用例。未覆盖只写进报告
- ❌ 把「没有同名测试类」当成未覆盖。未覆盖必须写成一句可观察行为，并写明现有用例证明了什么、没证明什么
