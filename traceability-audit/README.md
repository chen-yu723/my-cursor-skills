# traceability-audit

> 跨阶段追溯对齐审计。先核对设计决策的来源，再把通过对的决策、开发设计、测试用例和已生成代码对齐到同一组可观察规则上，标出不一致、未覆盖、来历不明。不启动系统。

执行步骤以同目录 `SKILL.md` 为准。本文件只说明何时用、要给什么、会得到什么。

## 安装与更新

规则在本仓库的 `traceability-audit/`。发布就是把这个目录推到 `main`。同事不改本地副本，用下面两条命令安装或更新。

首次安装（Cursor、Claude Code、Codex）：

```bash
npx skills add chen-yu723/my-cursor-skills --skill traceability-audit -g -a cursor claude-code codex -y --copy
```

规则改完并推到 `main` 之后，已安装的人执行：

```bash
npx skills update traceability-audit -g -y
```

更新会按仓库里的最新目录覆盖已安装副本。装完重新打开对话后再用。

## 做什么

只核对能在文档或代码里写出来的规则：谁、在什么状态、做什么、期望看到什么。

设计决策表是实现合同。有这张表时，先做来源核对，只有来源对得上的行才进入裁决基准，再拿去对开发设计、前端设计、用例和代码。

| 类型 | 含义 | 接下来做什么 |
|---|---|---|
| 不一致 | 同一条规则在两份材料里说法不同 | 来源已通过对的决策与代码或用例冲突时，按该决策改代码或改用例。来源未证实，或需求正文与已拍板结论不同，裁决写「待人工」，不自动改任一边 |
| 未覆盖 | 来源已通过对的规则，用例没有写成可观察行为 | 补用例。这是漏测，不写成缺陷。不按「没有同名测试文件」记。每条写明行为、代码位置、现有用例证明了什么、没证明什么 |
| 来历不明 | 代码或用例里出现了设计和用例都没写的分支、字段、常量 | 停下问人：补设计，或删代码 / 删用例 |

五类锚点：状态 / 枚举、错误文案、角色与端、接口与流程 key、字段约束（必填、长度、类型、格式）。按锚点抽，不逐行对文档。

## 材料各是什么

| 名称 | 是什么 | 怎么用 |
|---|---|---|
| 设计决策表 | 可选。后端、前端可以各有一份「决策结论」，每行一条 D | 两份都做来源核对，通过对的才当裁决基准。编号分开用，不要混成一套。没有这份文件时不编造 D 编号，改用开发设计或前端设计，报告注明裁决基准已切换 |
| 开发设计 | 后端的流程、数据模型、接口、状态怎么跳 | 按已通过对的决策落地。类名、锁、日志表不拿来判用例缺口。没有决策表时，从这里抽状态及下一跳、错误码、写明「不包含 / 禁止」的范围 |
| 前端设计 | 同版本、同需求下的 `*-前端设计.md`。页面入口、按钮显隐、文案、字段校验、跳转、内管还是客户端 | 阶段 A、B 只要这份文件存在就读。找不到则报告写「本轮无前端设计文档」。后端开发设计里顺带的页面说明不能代替它。配套的前端设计决策表与后端决策表同样做来源核对 |
| 来源文档 | 决策表「来源」列和文首「输入文档」点到的需求、澄清、接口 | 有设计决策表时必读。路径在决策表里就直接读，找不到再问。没有决策表则不读 |
| 测试用例 | 带编号和预期的用例 | 和通过对的规则对 |
| 代码 | 阶段 B 才需要。后端 Controller、Service、枚举；非低代码前端再加页面、路由、接口调用 | 只读，用搜索把用例对到代码。低代码页面只抽接口路径、枚举和文案。注释里写「已覆盖」或「别处测过」不算覆盖 |

## 来源核对

有设计决策表时，先于用例和代码对齐。逐行看「来源」：

| 核对结果 | 这条 D 怎么用 |
|---|---|
| 来源文档里能找到原句，原句推得出该结论 | 进入裁决基准 |
| 来源写明用户或产品已拍板，决策表状态为已批准，且拍板句与结论一致 | 进入裁决基准。需求正文另有不同说法时，这条改标待人工 |
| 来源为空、引用的章节不存在，或原句推不出该结论 | 不进入裁决基准。报告记「来源未证实」，不拿它改用例，也不拿它判代码缺陷 |

来源未证实的行先列出。开发设计若只实现了这些行，不把「开发设计没写」记成未覆盖。

## 两个阶段

| 阶段 | 什么时候用 | 输入 | 不做什么 |
|---|---|---|---|
| A | 开发设计和测试用例已有，代码还没有 | 开发设计、测试用例；同版本有前端设计就加上；有设计决策表（含前端决策表）时加上该表及其来源文档 | 不读代码。来源对不上的 D 不拿来改用例。后端设计与前端设计说法不同时记不一致、待人工 |
| B | 代码已经生成，测试还没跑起来 | 阶段 A 的材料，加上后端代码；非低代码前端再加页面、路由、接口调用 | 不启动服务，不跑测试，不改代码，不改用例。未覆盖按行为记，不按「没有同名测试文件」记 |

阶段 A 能看出规则没写死：0 与空、负数、空格、边界日、多方签署时主状态按一人还是全员、旁路失败是否挡住主流程、超时后能否再发、存量走哪条分支。

阶段 B 先判定前端是手写页面还是低代码。再只读源码和用例，用接口路径、枚举、错误文案、方法名把已有用例对到代码。一条用例对上某个文件，不算这个文件里的每个分支都已覆盖。代码形态另看：字段是否按设计赋值、两个角色是否共用一个模板变量、更新条件是否只有手机号、`||` 是否把 0 变成空、验证码或分页是否写死、热修是否在待发布分支、DDL 是否少字段。一条未覆盖写四项：行为、代码位置、现有用例证明了什么、没证明什么。建议动作只写「补用例」，本步不写用例。

白名单、注册中心、CDN、对方主数据错误、FTP 偶发断开，两阶段都不判。代码里已经写死的取数顺序、0 变空、主状态聚合，归阶段 B。

## 怎么触发

在对话里 `@traceability-audit`，并给出文件路径。

阶段 A：

```
@traceability-audit
阶段 A。设计决策表：D:\project\设计决策.md
开发设计：D:\project\开发设计.md
前端设计：D:\project\前端设计.md
测试用例：D:\project\测试用例.md
```

前端设计路径可以不写。同版本目录里有 `*-前端设计.md` 时 skill 自己去读；没有就在报告里写「本轮无前端设计文档」。配套的前端设计决策表同样要读。

来源文档的路径写在设计决策表的「输入文档」和「来源」列里，skill 自己去读。列里没有路径时再问。

阶段 B 在上面的材料之外给出代码目录，例如后端服务和前端工程。也可说：追溯审计、需求-设计-用例-代码对齐、漏测排查、设计决策落地核对、上线前一致性复查。

```
@traceability-audit
阶段 B。设计决策表、开发设计、前端设计、测试用例沿用阶段 A。
代码：D:\project\tbea-cust
代码：D:\project\tbea-spyPc-front
```

缺哪份材料就说明「该阶段无此输入」，不要用空文件凑数。

## 交付物

1. 来源核对结果：每条 D 是进入基准，还是「来源未证实」
2. 追溯矩阵：只含来源已通过对的规则，对应的用例、代码位置和状态（一致 / 不一致 / 未覆盖 / 来历不明）
3. 阶段清单：阶段 A 是用例反查设计和设计反查漏测。阶段 B 再加上代码字面量、按行为核对的未覆盖、来历不明
4. 分歧报告：类型、锚点、设计怎么说、用例怎么说、代码怎么写、建议动作、裁决。阶段 B 的未覆盖带上那四项

含糊措辞（通常、建议、视情况、待确认）单独列出，请人确认，不记成缺陷。

本 skill 不修改设计、用例或代码，也不启动服务、不跑测试。
